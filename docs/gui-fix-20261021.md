# AudioCast 0.1.1 — real-TV GUI and service repair

## Verified outcome

On the tested ARMv7 MStar LG TV (webOS build 20250429094550, WebAppManager Chrome 53.0.2785.34):

- The app is installed and its CSS, images and JavaScript load.
- The UI has a visible, styled IP/hostname and UDP-port form, a remote-operable on-screen editor, transport selection, status, diagnostics and advanced format settings.
- Homebrew bootstrap completes from the actual unprivileged app. The authenticated loopback API reports the background daemon online.
- A real GUI save persisted a temporary port change to native `config.json`. The original config was restored byte-equivalently as JSON; pending user form values were preserved. No audio capture or streaming was started for this test.
- Homebrew init.d background-service startup was observed after the full reboot preceding this repair. The corrected app keeps that service boot-enabled even with stream autostart off. The final binary and service are installed; a second reboot was not required or performed for the final update.
- The actual TV screenshot shows the complete default screen at 1920×1080 without horizontal overflow. Real-TV evidence is under `build/proofs/tv/` (not packaged or published as user data).

**Media playback capture remains unavailable.** The UI says so and blocks the hazardous sources instead of claiming a stream is working.

## Confirmed root causes

### Opaque local-file origin / CSP

The original TV logs explicitly refused `src/style.css`, the icon and both app scripts under `style-src 'self'`, `img-src 'self'` and `script-src 'self'`. This WebAppManager gives packaged `file://` documents an opaque origin, so `'self'` did not permit sibling resources. No scripts ran, which made Homebrew/ACL speculation premature.

The corrected CSP explicitly permits local `file:` assets while still prohibiting remote scripts, objects and forms; API network access remains limited to the two loopback endpoints. Computed text color and stylesheet count were verified in the actual TV engine, not inferred from a desktop screenshot.

### Different Homebrew calling conventions

These two APIs are not interchangeable:

```js
// Optional webOS.js SDK:
webOS.service.request('luna://org.webosbrew.hbchannel.service', {
  method: 'exec', parameters: { command: FIXED_HELPER_COMMAND },
  onSuccess: success, onFailure: failure
});

// Native bridge (present on the tested TV without webOS.js):
bridge.onservicecallback = callback;
bridge.call('luna://org.webosbrew.hbchannel.service/exec',
            JSON.stringify({ command: FIXED_HELPER_COMMAND }));
```

Bridge objects are retained until completion and both paths have a timeout. Only fixed management actions are accepted; receiver input is sent through the authenticated JSON API, never interpolated into root shell commands.

### Old web engine compatibility and UI state

- Replaced CSS Grid/flex-gap dependencies with Chrome-53-compatible flex layouts and explicit spacing.
- Added D-pad navigation within the on-screen editor, cancellation and focus restoration.
- Polling no longer overwrites unsaved form edits.
- Configuration changes are disabled during capture; unsafe devices and microphones cannot be selected.
- Service startup and streaming startup are separate settings. Manual streaming does not remove the service boot symlink.
- Boot hook initializes and secures an absent state directory before redirecting logs.
- Legacy BusyBox `timeout` uses `-t SECS`; GNU's positional form was failing on this TV. Both helpers now detect the supported form. This is not protection against uninterruptible kernel hangs.

## Tests

- 40 host-native process/ALSA-double/receiver/supervisor tests passed.
- 17 browser checks passed against the real native API, with explicit ALSA and Homebrew doubles. Real synthetic RTP packets reached a UDP receiver; this is not TV capture evidence.
- ARM cross-build and QEMU self-test passed (Debian ARM libc, separately from real-TV validation).
- Real-TV CDP checks: CSS/text visible, Homebrew bootstrap online, IP/port visible, boot enabled, no horizontal overflow, real form POST persistence and config restoration.
- `tools/tv-ui-smoke.cjs` can reproduce read-only inspection through an SSH-forwarded loopback debugger endpoint. It never starts capture or changes routing.

## Capture boundary / next gate

The MAD ALSA devices remain blocked because opening them previously wedged the kernel. Pulse monitors did not carry the tested media audio. DILE upload probes produced timed PCM callbacks but only the boot chime was nonzero; a usable third-party media route has not been established.

An actual read-only native-app request to `luna://com.webos.audio/state/get` returned `Denied method call "get" for category "/state"`. Homebrew exec works; that does not grant the app all private audio APIs. No firmware ACLs or audio routes were changed.

The audiod binary contains a string-valued loopback schema near speaker/microphone/Bluetooth on/off constants; that is **not proof of a safe TV-playback mirror**, and it is not shipped as an implemented backend. Further active vendor-routing tests cross the original no-routing-change constraint and require an explicit scope/risk decision. Do not market this version as working playback capture on this TV.
